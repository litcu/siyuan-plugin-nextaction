# NextAction 项目功能重构规格

状态：已发布到 GitHub Issue #1（`ready-for-agent`）

## Problem Statement

当前 NextAction 已经能够把思源文档标记为 Project，并提供项目总览、层级、看板、计划、甘特、Next Action 和 Review 等能力，但 Project 仍主要表现为 `taskType = project` 的父任务集合。

这造成几个用户可见问题：

- 用户无法在项目中稳定表达“最终要取得什么结果”（Outcome）和“满足什么条件才算真正完成”（Definition of Done，DoD）；
- 项目进度按所有非项目后代计算，阶段或父 Action 可能与叶子行动重复计数；
- 全局 Next Action、项目摘要和 Review 对 `someday`、开始日期和阻塞状态存在规则分叉；
- 项目完成可能由任务清空推断出来，但没有 Outcome/DoD 确认流程；
- 跨文档 Action 可以通过 `custom-na-parent` 归属项目，但取消项目身份时可能留下悬挂父关系；
- 项目 Review 仍主要按通用任务分组，不能以 Project 为唯一检查对象聚合风险；
- Outcome、DoD、Stage 一旦加入，必须贯穿属性、缓存、广播、RPC、MCP、AI 和前端编辑链路，不能只做界面字段。

用户需要的是一个嵌在思源笔记中的、以结果为中心的个人项目执行系统，而不是 Mini Jira、日历排程器或脱离笔记的 Todo List Plus。

## Solution

将 Project 明确建模为锚定在思源文档块上的有限结果承诺，将 Action 建模为推动结果发生的具体行动。

核心闭环为：

```text
收集 → 澄清 → 定义 Outcome / DoD → 规划 → Next Action
→ 执行 → 风险观察 → Project Review → 调整 → 确认完成
```

主要方案：

1. Project 的唯一身份是文档块上的 `custom-na-task = "2"` 项目标记；Outcome、DoD 和 Stage 标记不能单独使块成为 Project。
2. Action 可以在任意思源位置创建，通过现有 `custom-na-parent` 形成统一逻辑父关系；指向 Project 时表示项目归属，不要求物理移动。
3. Stage 是带有 `stage` 标记的 Action，可以有子 Action，也可以自己执行；它不引入第二套生命周期。
4. Outcome 使用单行纯文本，DoD 使用多行纯文本；属性是项目控制的唯一来源，正文只保存背景、方案、研究和决策记录。
5. Next Action 由共享领域谓词自动推导；`someday` 不能成为 Next Action，所有视图和 MCP 必须使用同一判断。
6. 项目进度只统计没有有效 Action 子节点的叶子 Action；有子节点的 Stage 或父 Action 展示子树进度但不重复计数。
7. 所有叶子完成只产生 `completionCandidate`；Project 必须经过用户确认 Outcome、DoD 和完成提示后才进入 `done`。
8. Project 进入 `done` 后新增或重新打开直接子 Action 时自动恢复为 `doing`。
9. Project Review 以 Project 为唯一队列项，多个风险合并为一次检查；周期 Review 复用现有 Review 字段，风险 Review 不依赖周期设置。
10. 首阶段不做 Timeboxing、容量预测、自动排程或 AI 自动写入；AI 只生成提案，写入必须先预览并由用户确认。现有显式 MCP 写入工具保持既有契约，未来如需 Agent 确认再设计 preview/apply 协议。

## User Stories

1. 作为个人用户，我希望把一个思源文档转换为 Project，以便用文档承载项目上下文和知识。
2. 作为个人用户，我希望在任意位置先捕获一个项目想法，即使只有标题，也能稍后逐步澄清。
3. 作为个人用户，我希望创建 Project 时可以选择自动创建新文档或使用已有文档，以适配快速捕获和已有方案两种场景。
4. 作为个人用户，我希望明确看到 Project 的唯一身份是项目标记，而不是误把 Outcome、DoD 或 Stage 字段当成项目类型。
5. 作为个人用户，我希望为 Project 填写一句话 Outcome，以便始终知道项目最终要取得什么结果。
6. 作为个人用户，我希望为 Project 填写多行 DoD，以便在关闭项目时检查真实完成条件。
7. 作为个人用户，我希望项目正文仍然是自由的思源笔记，以便记录背景、研究、方案、决策和复盘。
8. 作为个人用户，我希望正文中同名的 Outcome/DoD 内容不会静默覆盖项目属性，以便知道哪个内容会影响项目控制。
9. 作为个人用户，我希望在项目面板中直接编辑 Outcome 和 DoD，以便不用在属性面板和项目视图之间来回切换。
10. 作为个人用户，我希望在任意笔记中创建 Action 后把它加入 Project，以便保留原始笔记上下文。
11. 作为个人用户，我希望“加入项目”只改变逻辑归属，不移动思源块，以便低风险地整理行动。
12. 作为个人用户，我希望清楚区分“加入项目”和“移动到项目文档”，以便不会误把逻辑操作当成物理笔记移动。
13. 作为个人用户，我希望一个 Action 只能有一个逻辑父级，以便项目进度和责任不会被多个 Project 重复计算。
14. 作为个人用户，我希望 Project 可以拥有普通 Action 和 Stage，但不能嵌套另一个 Project，以便项目边界保持浅层、可理解。
15. 作为个人用户，我希望 Stage 可以有子 Action，也可以表达自身工作，以便在需要时同时支持阶段组织和阶段性交付。
16. 作为个人用户，我希望 Stage 的状态、日期、依赖和 Next Action 行为与普通 Action 一致，以便不需要学习第二套任务系统。
17. 作为个人用户，我希望有子节点的 Stage 不会和叶子 Action 重复计入项目进度，以便百分比反映实际工作项数量。
18. 作为个人用户，我希望没有子节点的 Stage 按叶子 Action 计入项目进度，以便孤立阶段仍然可以作为实际工作完成。
19. 作为个人用户，我希望看到每个 Stage 的子树进度，以便了解阶段推进情况而不影响项目总进度。
20. 作为个人用户，我希望空项目显示“待澄清”和 `0/0`，而不是一创建就显示为错误或阻塞。
21. 作为个人用户，我希望已进入 Planned/Active 但仍为空的项目显示“尚未拆解”风险，以便知道需要补计划。
22. 作为个人用户，我希望系统自动推导 Next Action，以便不用额外维护“下一步”标记。
23. 作为个人用户，我希望 `someday` 行动不会出现在 Next Action，以便将来/也许池不会污染当前执行列表。
24. 作为个人用户，我希望 Next Action 遵守开始日期预览窗口、依赖、顺序模式、等待和阻塞规则，以便候选行动真正可执行。
25. 作为个人用户，我希望项目总览、全局 Next Action、Review 和 MCP 对同一个行动给出一致的可执行判断，以便不会在不同视图看到矛盾结果。
26. 作为个人用户，我希望默认并行执行行动，以便快速捕获的项目不被隐式顺序限制阻塞。
27. 作为个人用户，我希望明确开启顺序模式或设置显式依赖后才阻塞后续行动，以便严格流程只在需要时出现。
28. 作为个人用户，我希望系统能显示逾期、等待、阻塞、没有下一步和项目尚未拆解等风险，以便主动控制项目。
29. 作为个人用户，我希望 `complete` 只表示项目已经确认完成，以便“所有行动完成”和“结果已经达成”不会混淆。
30. 作为个人用户，我希望所有叶子 Action 完成后收到“项目可能可以完成”的提示，以便开始关闭检查。
31. 作为个人用户，我希望完成确认中看到 Outcome、DoD 和未完成的非叶子节点，以便基于结果而不是任务数量关闭项目。
32. 作为个人用户，我希望 Outcome 或 DoD 为空时看到显著提醒，但仍可以在渐进式流程下确认完成，以便早期项目不会被强制填满字段。
33. 作为个人用户，我希望完成 Project 后新增或重新打开直接子 Action 时项目自动恢复为 Active，以便已完成状态不会掩盖新的未完成工作。
34. 作为个人用户，我希望可以手动关闭空项目，但必须看到“尚未拆解”的提醒，以便明确这是主动放弃详细规划，而非系统误判。
35. 作为个人用户，我希望项目 Review 以一个项目作为队列项，而不是同一项目的多个风险分别占位，以便一次完成项目校准。
36. 作为个人用户，我希望多个项目风险在 Review 中合并显示，并能在项目内逐项处理，以便保持 Review 流程简洁。
37. 作为个人用户，我希望没有 Review 周期的项目在出现风险时仍进入 Review，以便风险不会因关闭周期而隐藏。
38. 作为个人用户，我希望没有周期、没有风险的项目也可以手动立即回顾，以便保持完整的项目闭环。
39. 作为个人用户，我希望 Review 能检查 Outcome、DoD、计划、Next Action、Waiting/Blocked 和项目状态，以便重新同步现实与计划。
40. 作为个人用户，我希望取消 Project 身份不会删除项目文档或 Action，以便撤销项目管理不会破坏笔记内容。
41. 作为个人用户，我希望取消 Project 身份时直接归属该项目的 Action 会被清理归属，以便不会留下悬挂项目关系。
42. 作为个人用户，我希望被清理的 Action 能按原来的结构父任务规则重新归属，以便保留思源文档结构语义。
43. 作为个人用户，我希望更深层 Action 不会因取消项目而被递归改写，以便局部任务树保持稳定。
44. 作为个人用户，我希望外部直接修改项目属性时也能触发同样的项目关系清理，以便系统不会因不同入口产生孤儿关系。
45. 作为个人用户，我希望 Project 不能成为普通 Task 的子项，以便项目不会嵌入不适合承载项目语义的任务节点。
46. 作为个人用户，我希望 Project 不能成为另一个 Project 的子项，以便首阶段保持单层项目组合。
47. 作为个人用户，我希望循环父关系和不存在的父关系会被拒绝或安全修复，以便项目树不会崩溃。
48. 作为个人用户，我希望项目总览、层级、看板、计划和甘特视图继续可用，以便新领域模型不会破坏已有观察方式。
49. 作为个人用户，我希望总览、项目详情、Next Action 和 Review 成为主路径，以便不同视图各自服务于选择、定义、执行和校准。
50. 作为个人用户，我希望 AI 能根据笔记和项目上下文提出 Outcome、DoD、Action 或 Review 建议，以便减少整理成本。
51. 作为个人用户，我希望 AI 不能绕过确认直接改变项目身份、归属、状态、结构或删除内容，以便笔记和项目承诺始终由我控制。
52. 作为个人用户，我希望未来若允许外部 Agent 写入，能先预览变更集合并使用确认令牌提交，以便自动化仍然可审查。
53. 作为个人用户，我希望首阶段不引入时间盒、容量预测和自动排程，以便项目流程保持轻量并避免伪精确。
54. 作为个人用户，我希望项目支持材料后续可以从块引用、文档引用和直接反向链接聚合，以便利用思源原生知识关系。
55. 作为个人用户，我希望支持材料只是只读上下文，不会自动变成 Action 或影响项目进度，以便知识链接不会产生意外承诺。

## Implementation Decisions

- Project 的唯一身份由文档块类型和项目标记共同决定；Outcome、DoD、Stage 不是身份判定条件。
- Project 使用现有任务状态表达 Draft、Planned、Active、On Hold、Someday 和 Completed，不新增独立生命周期状态。
- `custom-na-parent` 继续表示统一逻辑父关系；指向 Project 时表示项目归属，指向普通 Task 时表示父任务。
- 首阶段禁止 Project→Project 和 Project→普通 Task；允许 Action/Stage→Project、Action/Stage→Task，并保留循环校验。
- 取消 Project 身份必须走统一领域清理路径：清除项目标记，清理直接指向该项目的父关系，让这些 Action 回到结构父任务规则；不递归修改更深层子项。
- `custom-na-kind` 是核心保留属性，仅允许普通 Action 使用 `action` 或 `stage`；Project 不设置该字段，且不能被自定义字段覆盖。
- Outcome 是单行纯文本；DoD 是多行纯文本；属性是控制来源；项目正文不自动解析、不双向同步。
- 新增字段必须贯穿属性常量、共享任务类型、缓存和仓储、增量广播、RPC/前端桥接、MCP DTO/patch、AI schema 和前端详情编辑。
- 需要逐项追踪的 DoD 条件必须建成 Action，不建立第二套 DoD 清单状态模型。
- 叶子 Action 定义为没有有效 Action 子节点的 Action；没有子节点的 Stage 可作为叶子；有子节点的 Stage 展示子树进度但不重复计数。
- Project 后代中的嵌套 Project不参与父项目进度；由于首阶段禁止嵌套 Project，非法关系应在写入时拒绝。
- 空项目显示 `0/0` 和待澄清；Draft 空项目不产生异常风险，Planned/Active 空项目产生尚未拆解风险；空项目没有自动完成候选，但可在提醒后手动关闭。
- `complete` 只表示 Project 已确认进入 `done`；叶子完成但未确认使用 `completionCandidate`，不能提前改变健康度。
- Project 完成后新增或重新打开直接子 Action 时自动恢复为 `doing`。
- Next Action 使用共享领域谓词：排除 Project、done、waiting、someday、inbox、未来开始窗口和被依赖/顺序阻塞的行动；所有消费者必须共用该谓词。
- 开始日期的业务语义是可开始日期；`startPreviewDays` 是候选展示窗口配置，不得由不同视图自行解释。
- Project Review 以 Project 为唯一队列项，风险在项目内聚合；周期到期和风险触发是两种来源；支持手动立即回顾。
- Review 数据契约必须能传递项目摘要、健康度、完成候选和风险集合，并由 Project Domain Summary 统一计算。
- “加入项目”只写入逻辑父关系；“移动到项目文档”是独立的物理块移动操作，不属于 Phase 1。
- 物理移动实现前必须确定目标容器、列表项/内容块/子树保留、跨文档失败回滚、循环保护、显式父关系保留和撤销行为。
- Project Support 后置到 Phase 2，仅支持一层明确块引用、文档引用和直接反向链接；去重、只读展示、不递归、不参与进度和完成。
- AI 只生成提案，AI 产生的写入必须经过预览和用户确认；现有显式 MCP 写入工具在 preview/apply 协议建立前保持当前契约，不宣称已有确认通道。
- 实施顺序采用垂直切片：共享字段/数据通路 → 父关系与清理 → 叶子进度/完成确认 → Next Action/健康度 → Review 契约 → UI；物理移动和支持材料后置。

## Testing Decisions

- 测试只验证外部行为和领域结果，不断言私有实现细节或具体组件内部结构。
- 最高测试 seam 是共享 Project Domain Summary/判定服务；ProjectView、Next Action、Review 和 MCP 都通过它验证一致性。
- 第一组测试覆盖 Project 身份判定：文档块 + 项目标记才是 Project，Outcome/DoD/Stage 不可单独改变身份，普通块不能转换为 Project。
- 第二组测试覆盖父关系矩阵：跨文档 Action 归属 Project、Project→Project 拒绝、Project→Task 拒绝、循环和不存在父级处理、取消项目只清理直接子关系。
- 第三组测试覆盖叶子遍历：叶子 Action 进度、Stage 有子项时不重复计数、无子项 Stage 计入、空项目 `0/0`、非法嵌套 Project 不计入父项目。
- 第四组测试覆盖 Next Action 共享谓词：someday、waiting、inbox、未来开始、依赖和顺序阻塞均不进入候选；内核查询、ProjectView、Review 和 MCP 对相同输入结果一致。
- 第五组测试覆盖完成候选和生命周期：叶子完成不自动 done、Outcome/DoD/非叶子提示、用户确认后 done、done 后新增/重开直接子 Action 自动恢复 doing。
- 第六组测试覆盖项目 Review：周期到期、风险触发、多个风险合并为一个项目项、风险消失后移除、手动立即回顾和 reviewDate 更新语义。
- 第七组测试覆盖数据通路：Outcome、DoD、Stage 的创建、更新、清空、权威回读、缓存更新、增量广播、RPC、MCP 展示和 AI 上下文可读性。
- 所有原始 bug 修复都要在最相关测试文件中增加带 `// Regression: ...` 注释的回归测试。
- 先运行纯逻辑和内核行为测试，再运行完整 `pnpm test`、类型检查、主题检查和构建；涉及 Svelte 或主题样式时补充 `pnpm run check:theme`。
- 物理移动实现后必须增加跨文档移动失败回滚、block ID 保留、子树保留、循环保护和撤销行为测试。

## Out of Scope

- Timeboxing、日历容量、容量预测和自动排程。
- Deadline Risk、Overcommitment 和基于估时的预测性控制。
- Project→Project 嵌套、无限层级、复杂 Deliverable/Milestone/Subproject 对象。
- 独立 DoD 清单状态模型、DoD Markdown 解析和自动完成判定。
- AI 自动写入、自动改状态、自动移动块、自动删除和未经确认的项目重规划。
- 外部 Agent 的 preview/apply 确认协议；该协议需要独立设计后再进入范围。
- Project Support 的递归引用网络、手动知识图谱和自动资料转 Action。
- 物理移动 Action 的 Phase 1 实现；首阶段只交付逻辑“加入项目”。
- 历史兼容性和已上架用户迁移；当前插件尚未上架，可以按新领域模型调整未发布数据结构。

## Further Notes

- 当前代码已经存在项目摘要、项目树、Next Action、Review 和 MCP 等多个消费者，但它们对叶子、开始日期和 `someday` 的判断存在分叉。实现时必须先建立共享领域判断，再接入各消费者。
- 当前代码已有 `custom-na-parent` 的显式父级优先结构父级回退语义；取消项目后清空父关系会回到结构父任务规则，这必须在 UI 文案和回归测试中明确。
- 当前代码的通用 `removeTask` 与直接清除项目标记的更新路径并不等价；Project 身份取消必须新增或复用统一领域命令，不能让不同入口留下不同清理结果。
- 当前代码没有物理块移动 RPC；不要把 `reorderTask` 描述成物理移动。
- 当前代码的 MCP 写入工具是显式直接写入工具；本规格只约束 AI 提案路径，未来若扩大到外部 Agent，必须先补充确认协议和权限边界。
- 设计基线记录在领域上下文和 ADR 中；本规格是面向实现代理的执行版本，后续实现发现不可逆架构分叉时应新增 ADR，而不是静默修改本规格。
